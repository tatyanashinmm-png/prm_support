# Oracle-синк

Локальный агент — выполняет заданный в дашборде SQL-запрос к вашей Oracle
БД и отправляет результат в backend. Живёт **на вашей машине** (там, где
есть сетевой доступ к Oracle), не в Docker и не на сервере — backend
доступа к Oracle не имеет и иметь не должен.

## Установка

```
cd oracle-sync
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Скопируйте `.env.example` в `.env` и заполните:

```
cp .env.example .env
```

- `BACKEND_URL` — адрес вашего backend (сейчас `http://31.58.171.228:8000`)
- `ORACLE_HOST`, `ORACLE_PORT`, `ORACLE_SERVICE` — куда подключаться
- `ORACLE_USER`, `ORACLE_PASSWORD` — доступ (попросите у администратора Oracle,
  права нужны только на чтение — `SELECT`)

Instant Client ставить не нужно — `python-oracledb` по умолчанию работает
в thin-режиме, без нативных библиотек Oracle.

## Сам SQL-запрос — не здесь

Запрос не хранится в этом агенте — он подтягивается из `/settings`
backend'а (то же поле, что редактируется в дашборде на «Настройки» →
«Синхронизация клиентов из Oracle»). Поменяли запрос в дашборде — агент
на следующий вызов уже использует новую версию, ничего в коде трогать
не нужно.

Скрипт понимает и «сырые» колонки реального биллингового запроса, и
заранее сокращённые алиасы — можно писать SQL любым способом:

| Колонка в Oracle | Поле в системе | Что это |
|---|---|---|
| `ID_CONTRACT_INST` | `billing_contract_id` | id подписки в биллинге |
| `V_EXT_IDENT` | `billing_contract_number` | номер подписки |
| `V_LONG_TITLE` | `name` | наименование клиента (обязательное) |
| `VID_GROUP` | `tg_group_id` | id группы в Telegram (обязательное) |
| `TARIFF_PLAN_NAME` | `tariff_name` | наименование тарифа |
| `V_SERVICE_STATUS` | `subscription_status` | статус подписки, видно в карточке клиента |
| `SERVICE_DT_START` | `connected_at` | дата подключения — по ней аналитика отличает новых/действующих клиентов, тоже видно в карточке |

Регистр колонок не важен (`VID_GROUP` и `vid_group` — одно и то же).
Цены тарифа (`tariff_price`) в реальном биллинговом запросе нет — поле
просто останется пустым, пока не появится источник для него.

**Дедупликация.** Реальные запросы через JOIN (например, с таблицей услуг)
нередко отдают одну и ту же подписку по нескольку раз подряд — скрипт
сам схлопывает такие дубли по `tg_group_id`, берёт первую строку на
группу, а сколько дублей убрал — пишет в лог.

## Запуск

**Разовый запуск** (для cron):
```
python sync.py --once
```

**Режим ожидания** — крутится в фоне, проверяет раз в минуту (`POLL_INTERVAL_SEC`
в `.env`), не нажали ли «Запустить синхронизацию» в дашборде:
```
python sync.py --loop
```

### Через cron (регулярный автосинк, например раз в сутки в 06:00)

```
crontab -e
```
добавить строку (поправьте пути под себя):
```
0 6 * * * cd /Users/tanya/.../oracle-sync && venv/bin/python sync.py --once >> sync.log 2>&1
```

### Через launchd (чтобы `--loop` жил постоянно, переживал перезагрузку Мака)

Проще всего через `launchctl` с `.plist`-файлом — если понадобится,
можно расписать отдельно, это не входит в MVP.

## Как это работает с дашбордом

- Кнопка «Запустить синхронизацию» в «Настройки» ставит флаг
  `oracle_sync_requested = true` через обычный `PATCH /settings`.
- Агент в режиме `--loop` видит флаг на следующей проверке, выполняет
  синк, backend сам сбрасывает флаг и проставляет `oracle_last_sync`.
- Время последнего синка видно в сайдбаре дашборда и в самой карточке
  настроек.
- В режиме `--once` (через cron) кнопка в дашборде не имеет смысла —
  флаг некому подхватить между запусками cron. Для крон-режима синк идёт
  только по расписанию.
