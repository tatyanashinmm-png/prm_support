# История изменений

Сжатая история развития по этапам (даты не фиксировались). Полный подробный журнал прежних
доработок сохранён в [`archive/README-history.md`](archive/README-history.md); часть его
инструкций устарела.

## Этапы

**1. Основа.** Backend на FastAPI и PostgreSQL по контракту из архитектурного документа; модели,
CRUD, docker-compose; bot-collector на aiogram; LLM-конвейер (категоризация, дневная сводка) с
эвристиками на случай недоступности ИИ; тестовые данные (`seed`); фронтенд по кликабельному
прототипу.

**2. Клиенты и аналитика.** Oracle-синк (локальный агент, нативные имена колонок биллинга,
дедупликация); тариф, статус подписки, дата подключения, VIP; период 7/30/90/произвольный;
сравнение периодов; категории (переименование для всех тикетов); платная доработка (план/факт);
название чата из Telegram; SLA в рабочих минутах (МСК, выходные, праздники); индексы БД,
GZip, устранение N+1 в списке клиентов.

**3. Маршрутизация и управление тикетами.** Реплаи → точный тикет; категории при работающем ИИ;
последний открытый тикет при недоступном ИИ; объединение, разделение, удаление тикетов;
оркестрация нескольких провайдеров ИИ по приоритету.

**4. Панель обращения.** Редизайн по прототипу, единый стиль выпадающих списков, кастомные
селекты вместо `<select>`, ссылки вида `?ticket={id}`, URL-роутинг разделов.

**5. «Пульс поддержки».** Редизайн по прототипу: навигация по дням с календарём, дельты «к вчера»,
единая очередь с вкладками и фильтрами, блоки обязательств, сводка ИИ, тумблер «ИИ-ассистент»,
тост «Отменить» при закрытии; последующие доработки по замечаниям (порядок и названия групп,
формат времени ожидания, дата создания в «С прошлых дней», фильтр по категории с поиском,
исключение дублей между очередью и блоками обязательств).

**6. Инфраструктура.** Деплой на HostVDS через docker compose, ночные бэкапы с копией на Мак.
Схема БД развивается без Alembic: `create_all` для новых таблиц и ручные миграции для колонок.

**7. Участники переписки.** Числовой `sender_tg_id`, список «Известные участники» с добавлением
в агенты, пересчёт роли задним числом в обе стороны, починка по имени для старых сообщений.

**8. Статус «Ожидание ответа клиента».** Автоматические переходы (ответ команды → ожидание,
сообщение клиента → снова открыто), заморозка SLA в ожидании, три состояния ответа, чип «N новых»
и отметка «прочитано», группа «Ждут ответа клиента», фильтр «Есть новые сообщения», блок
«Просроченные обязательства»; «агент» → «команда PRM»; автозакрытие отключено.

**9. Панель обращения, вторая итерация.** Режим разделения (шаги, `Shift`+клик, «Перенести/
Копировать»), меню «⋯», объединение в закреплённой области, копирование номера, поле
«Комментарий», «Наименование обращения», сайдбары закрываются только крестиком/«Отмена»,
перенос длинных строк, растущее поле названия.

**10. Авторизация.** Пользователи, вход по паролю и через Google (код готов, не настроен), JWT,
смена пароля, журнал действий; защита всех эндпоинтов; общий ключ бота `BOT_SERVICE_KEY`.

**11. «Обращения» как таблица.** Сортировка, выбор строк, экспорт CSV, пагинация, период в
строке фильтров, колонка «Срок», SLA не считается при заданном сроке, вкладка «Задачи со сроком»,
создание обращения боковой панелью, значок ₽ вместо чипа «Доработка».

## Инциденты и исправления

Что ломалось на практике — чтобы не повторять.

| Что случилось | Причина | Исправление |
|---|---|---|
| Ответы агентов не сохранялись; в интерфейсе «Failed to fetch» при смене статуса | В БД остался старый CHECK на `status` без `waiting_client`; сообщение и статус коммитились одной транзакцией — откатывались вместе | Миграция ограничения; сообщение сохраняется **отдельным** первым коммитом |
| Backend падал при старте после включения авторизации | `google-auth` требует пакет `requests`, его не было в зависимостях | `requests` добавлен в `requirements.txt` |
| Бот перестал получать сообщения после включения авторизации | Бот запрашивал закрытый теперь `/settings`; необработанное 401 валило процесс | Отдельный `GET /ingest/bot-config` с ключом `BOT_SERVICE_KEY`; при сбое бот не отключается от Telegram |
| Сохранение обращения со сроком возвращало 500 | В запись журнала попадал объект `date`, JSONB его не принимает; сбой шёл после сохранения тикета | `log_action` приводит данные к JSON и никогда не роняет запрос |
| Закрытое сегодня обращение пропадало из «Пульса» | «Закрытые» строились по дате создания, а не закрытия | Фильтр по `closed_at`; тот же принцип для счётчика «Закрыто» в сводке |
| Части длинного сообщения менялись местами после переноса | Сортировка только по времени (секунды), у частей оно совпадает | Порядок: `sent_at` → `tg_message_id` → `id` |
| Сообщения с файлами не попадали в переписку | Бот читал только `message.text`, у файла текст в `caption` | Берётся `text` или `caption` |
| Агент отображался как «клиент» | Роль фиксируется при приёме, а `sender_tg_id` появился позже | Пересчёт по id и по имени |
| Выпадающий список внутри прокручиваемой формы не открывался | Панель обрезалась родителем с `overflow` | Списки рисуются порталом в `<body>` |
| Данные в карточке клиента не обновлялись / экран мигал | Подписку на обновления убирали целиком, чтобы остановить мигание | Ключ контекста: загрузка показывается при смене клиента/периода, при фоновом обновлении — подмена на месте |
| Логи для разбора инцидента пропали | `up -d --build` пересоздаёт контейнер вместе с его логами | Смотреть логи до пересборки |
