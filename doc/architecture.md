# Архитектура Support Desk

Дашборд для анализа обращений клиентов в Telegram-чатах поддержки: бот собирает
сообщения, backend группирует их в обращения (тикеты), считает SLA и метрики,
ИИ помогает с категоризацией и дневными сводками, менеджеры работают в
веб-интерфейсе.

Документ описывает **текущее фактическое состояние** системы. Что запланировано,
но не сделано, собрано в разделе [«Известные ограничения»](#известные-ограничения-и-риски).

## 1. Компоненты

```
 Telegram-группы клиентов
          │  long polling (aiogram)
          ▼
 ┌──────────────────┐  POST /ingest/message        ┌─────────────────────────────┐
 │  bot-collector   │ ───────────────────────────► │  Backend (FastAPI)          │
 │                  │ ◄─ GET /ingest/bot-config ── │  ├ REST API (JWT)           │
 └──────────────────┘   (ключ BOT_SERVICE_KEY)     │  ├ Планировщик (APScheduler)│
                                                   │  └ LLM-адаптер              │──► Gemini / Groq /
 ┌──────────────────┐        JWT (Bearer)          │                             │    OpenRouter
 │ Frontend (React) │ ───────────────────────────► │                             │
 │ nginx, статика   │                              └──────────────┬──────────────┘
 └──────────────────┘                                             │
                                                          ┌───────▼────────┐
 ┌──────────────────┐  GET /settings, POST /clients/sync│  PostgreSQL 16 │
 │ oracle-sync      │ ──────────────────────────────► │                │
 │ (на локальной    │  (см. «Известные ограничения»)   └────────────────┘
 │  машине)         │
 └──────────────────┘
```

| Компонент | Технология | Где живёт | Назначение |
|---|---|---|---|
| **backend** | Python 3.12, FastAPI, SQLAlchemy 2, APScheduler | docker-compose, порт 8000 | REST API, бизнес-логика, планировщик, LLM-адаптер |
| **bot-collector** | aiogram 3, httpx | docker-compose | Слушает групповые чаты, пересылает сообщения в backend |
| **frontend** | React 18, Vite, lucide-react; отдаётся nginx | docker-compose, порт 5173 → 80 | Веб-интерфейс |
| **db** | PostgreSQL 16 | docker-compose, порт 5432 | Основное хранилище |
| **oracle-sync** | Python, `oracledb` | Локальная машина с доступом к Oracle (вне docker-compose) | Забирает клиентов из биллинга |
| **backup** | bash, cron | Сервер + Mac | Ночные дампы БД и их копирование |

**Не реализовано:** bot-digest (отправка сводок и напоминаний в Telegram) — сейчас
`POST /digest/send` только помечает сводку отправленной.

## 2. Модель данных (PostgreSQL)

создаёт **только отсутствующие таблицы** и не добавляет колонки в существующие —
изменения схемы существующих таблиц делаются вручную, см.
[operations.md → Миграции](operations.md#миграции).

случаен.

### users — пользователи
`id` (UUID), `email` (unique, в нижнем регистре), `name`, `password_hash` (bcrypt, может
быть пуст), `google_sub` (unique, может быть пуст), `role` (задел под ролевую модель,
не используется), `is_active`, `created_at`. **CHECK:** должен быть хотя бы один способ
входа — пароль или Google.

`id`, `user_id` (пуст — действие системы), `user_email` (копия на момент действия),
`action`, `target_type`, `target_id` (строка), `details` (JSONB), `created_at` (индекс).

## 3. Жизненный цикл обращения

### 3.1 Статусы и автоматические переходы

| Событие | Что происходит |
|---|---|
| Первое сообщение клиента, подходящего тикета нет | Создаётся тикет `open`; категория, тема и уверенность ставятся ИИ (или эвристикой) |
| Ответ команды (`sender_type=agent`) | `first_response_at` заполняется, если был пуст; статус → **`waiting_client`** (ход за клиентом) |
| Новое сообщение клиента в тикете `waiting_client` | Статус → **`open`** автоматически |
| Реплай на сообщение закрытого тикета | Тикет открывается заново. Сообщение без реплая закрытые тикеты не выбирает — создаётся новый |
| Закрытие (кнопка, панель тикета) | `status=closed`, `closed_at` проставляется, если пуст |
| Ручная смена статуса | Возможна в панели тикета на любой из статусов |

`pending_confirm` — устаревший статус AI-подсказки «предлагаю закрыть». Задача автозакрытия
**отключена**, новых тикетов в этом статусе не появляется; значение оставлено в CHECK и в
интерфейсе для старых данных.

### 3.2 Состояние ответа (`response_kind`)

Считается на backend (`business_hours.ticket_response_status`) и приходит в каждом тикете:

| `response_kind` | Условие | Что означает `wait_business_min` |
|---|---|---|
| `no_response` | Ответа команды не было | Растёт от первого сообщения клиента |
| `waiting_us` | Ответ был, но клиент написал ещё раз, и ответа на это нет | Растёт от последнего такого сообщения клиента |
| `waiting_client` | Ответили, новых сообщений клиента нет | **Заморожено** на времени до первого ответа — SLA не растёт, пока ход за клиентом |
| `closed` | Тикет закрыт | Время до первого ответа (или до закрытия, если ответа не было) |

Метрика «среднее время ответа» использует отдельную функцию
`first_response_business_minutes` — историческое время до первого ответа, не текущее состояние.

### 3.3 SLA

- Время считается в **рабочих минутах**: рабочие часы, рабочие дни и праздники из настроек,
  часовой пояс **Europe/Moscow** независимо от часового пояса сервера.
- **Нарушение SLA** = тикет не закрыт **и** не в `waiting_client` **и** `wait_business_min > attention_after_min`
  **и** **нет срока исполнения**.
- Если у обращения задан `due_date`, SLA по нему **не считается** (ориентир — срок): такие
  обращения не попадают в «Нарушен SLA», красную плашку и подсветку, в таблице вместо
  времени ожидания — «SLA не считается», в панели тикета — пометка вместо шкалы.
  Условие продублировано на backend (`GET /tickets?view=sla_breach`).

### 3.4 «Новые сообщения» и «прочитано»

- `new_message_count` — число сообщений клиента **после последнего сообщения команды**.
- Чип «N новых» гасится, если `agent_seen_at` ≥ времени последнего сообщения клиента.
  Отметить можно кликом по чипу или автоматически — при открытии панели тикета.
- «Прочитано» **не влияет** на статус и SLA: прочитать ≠ ответить. Новое сообщение клиента
  снова показывает чип.

### 3.5 Обязательства и обещания

«Обязательство» — обращение со срок исполнения (`due_date`). Раздел «Обещания» и блоки в
«Пульсе поддержки» строятся по нему. Бакеты: `overdue` (срок прошёл), `today`, `week`
(срок в будущем), `done` (закрытые). Кнопка «выполнено» в разделе «Обещания» **не закрывает**
тикет, а очищает `promise_text` и `due_date`.

### 3.6 Объединение и разделение

- **Объединение**: сообщения тикета переносятся в выбранный открытый тикет того же клиента,
  исходный тикет удаляется.
- **Разделение**: выбранные сообщения переносятся (`move`) или копируются (`copy`) в новый
  тикет того же клиента. Название по умолчанию — начало первого выбранного сообщения (≤120
  символов, переносы схлопнуты); `first_response_at` нового тикета = самое раннее сообщение
  команды среди перенесённых.
- **Удаление тикета**: сообщения не удаляются, а отвязываются (`ticket_id = NULL`).

## 4. Приём сообщений и маршрутизация

Эндпоинт `POST /ingest/message` (вызывается ботом) определяет роль отправителя и тикет.

**Роль:** `sender_type=agent`, если `sender_tg_id` входит в `agent_tg_ids`. Роль
фиксируется в сообщении в момент приёма; при изменении списка агентов старые сообщения
пересчитываются вручную («Настройки» → «Известные участники переписки» → «Синхронизировать
историю»; для сообщений без `sender_tg_id` — «…и по имени»).

**Маршрутизация — по приоритету** («открытый» здесь — любой не закрытый тикет, включая `waiting_client`):
1. Telegram-реплай на известное сообщение → однозначно тот же тикет, без ИИ.
2. Сообщение клиента без реплая, ИИ доступен → открытый тикет клиента с той же категорией; иначе новый.
3. Сообщение клиента без реплая, ИИ недоступен (эвристика менее надёжна) → последний открытый тикет клиента; иначе новый.
4. Сообщение команды без реплая → последний открытый тикет клиента.

**Надёжность сохранения.** Сообщение сохраняется **первой, отдельной транзакцией**. Статус
тикета и `first_response_at` применяются вторым коммитом: сбой на втором шаге (например,
несоответствие схемы БД) не теряет само сообщение. Тот же принцип у журнала действий —
сбой записи в журнал не ломает сохранённое действие.

**Бот** принимает текст и подписи к файлам; сообщения без текста и подписи (стикеры, файлы
без подписи) пропускаются с записью в лог. Неизвестная группа (нет клиента с таким
`tg_group_id`) отклоняется с предупреждением в логе.

## 5. ИИ

LLM-адаптер (`llm.py`) работает через OpenAI-совместимый формат: Gemini, Groq, OpenRouter.
Провайдеры пробуются **по очереди сверху вниз**; пропускается тот, у кого пуст ключ, выключен
`enabled` или запрос упал (сеть, лимит, неверный ключ). Если не ответил ни один — работают
эвристики по ключевым словам, приложение остаётся рабочим без ИИ.

| Функция | Где применяется |
|---|---|
| Категоризация (`categorize_ticket`) | Создание тикета при приёме сообщения; задача планировщика для тикетов с категорией «Не определено» |
| Дневная сводка (`generate_daily_summary`) | Планировщик и кнопка «Перегенерировать» |
| Автозакрытие (`suggest_close`) | Отключено |

Переключатель «ИИ-ассистент» в «Пульсе поддержки» скрывает ИИ-блоки страницы (сводку,
статус подключения) — это локальная настройка браузера, не серверная.

## 6. Планировщик

| Задача | Периодичность | Что делает |
|---|---|---|
| `categorize` | 1 мин | Категоризирует до 20 тикетов с категорией «Не определено» |
| `daily_digest` | проверка раз в 5 мин | Если включено, настало время (МСК) и сводки за сегодня ещё нет — генерирует её |
| `autoclose` | **отключена** | — |

## 7. Авторизация и журнал действий

- **Вход:** логин/пароль (`POST /auth/login`) или Google (`POST /auth/google`, id_token,
  проверяется через `google-auth`; пользователя нужно завести заранее, автосоздания нет).
  Google-аккаунт привязывается к существующему пользователю с тем же email.
- **Сессия:** JWT HS256 на 14 суток, хранится в `localStorage`, уходит в `Authorization: Bearer`.
  Ответ 401 сбрасывает сессию и показывает экран входа.
- **Что защищено:** все эндпоинты, кроме `POST /ingest/message`, `GET /ingest/bot-config`
  (закрыт отдельным ключом), `POST /auth/login`, `POST /auth/google`, `GET /auth/config`, `GET /health`.
- **Пользователи:** заводятся в «Настройки → Пользователи» (или CLI для первого). Пароль ≥ 8 символов.
  Свой пароль меняется в «Мой аккаунт»; админ может сбросить чужой. Деактивация блокирует вход.
- **Роли:** отсутствуют — все вошедшие равны в правах (`users.role` — задел).
- **Журнал** (`audit_log`, раздел «Журнал действий») фиксирует: вход, смену пароля, создание/
  изменение/удаление тикетов, объединение, разделение, создание/изменение/удаление клиентов,
  сохранение настроек (только **названия** ключей, без значений), переименование категорий,
  пересчёт ролей отправителей, действия над пользователями.
  Не логируются: «выполнено» в обещаниях, `mark-seen`, приём сообщений, синк клиентов,
  генерация/отправка сводки.

## 8. Время и даты

- Рабочие часы и время срабатывания сводки — **МСК**.
- Границы периодов в API (`date_from`/`date_to`, `days`) считаются по **UTC**; бакеты обещаний и
  дневная сводка используют дату сервера. Фронтенд группирует «сегодня/вчера» по локальному
  времени браузера. На границе суток (около 21:00–03:00 МСК) возможны расхождения.

## Известные ограничения и риски

### Функциональные
1. **oracle-sync не работает с включённой авторизацией.** Агент запрашивает `GET /settings` и
   `POST /clients/sync` без токена и получает 401. Нужен служебный доступ (по аналогии с
   `BOT_SERVICE_KEY` у бота).
2. **bot-digest не реализован**; `POST /digest/send` — заглушка; `bot_digest_token`,
   `auto_promise`, `remind_before_due` только хранятся.
3. `POST /settings/test-key` — заглушка. `POST /tickets/run-autoclose-check` вызывает отключённую задачу.
4. Экспорт — **CSV** (не `.xlsx`).
5. `closed_at` не сбрасывается при переоткрытии, поэтому счётчик «Закрыто» в сводке
   (считается по `closed_at`) может включать переоткрытые тикеты.
6. Сообщения, не дошедшие до базы (сбои приёма), автоматически не восстанавливаются: Telegram
   хранит неполученные обновления до 24 часов. Для более давней истории нужен импорт из
   экспорта чата Telegram Desktop — скрипта пока нет.
7. Нет Alembic — изменения схемы делаются вручную.
8. Вход через Google требует домена и HTTPS; сейчас приложение работает по HTTP, `google_client_id` не задан.
9. Nginx-образ фронтенда без SPA-fallback (нет `try_files`): прямой заход на адрес вида `/feed`

### Безопасность (по убыванию важности)
1. **`GET /settings` отдаёт все ключи, включая `jwt_secret`**, токены ботов и API-ключи ИИ,
   любому вошедшему пользователю. С `jwt_secret` можно подделать токен. Секреты нужно
   исключать из ответа или маскировать.
2. **Порт PostgreSQL (5432) опубликован на `0.0.0.0`** с паролем по умолчанию `support`
   (`docker compose ps` показывает `0.0.0.0:5432->5432`). Docker обходит правила `ufw`, поэтому
   порт, скорее всего, доступен из интернета — проверить с другой машины: `nc -zv 31.58.171.228 5432`.
   Нужно убрать `ports` у `db` или привязать к `127.0.0.1` (`"127.0.0.1:5432:5432"`) и сменить пароль.
3. **`POST /ingest/message` открыт без ключа**, порт 8000 виден снаружи — любой может
   отправить выдуманное сообщение. Закрывается тем же `BOT_SERVICE_KEY`.
4. Приложение работает по **HTTP** (пароли и токены идут открытым текстом); CORS `*`;
   JWT в `localStorage`.
5. Секреты (токен бота, ключи ИИ) хранятся в БД **открытым текстом**.
6. Нет ограничения числа попыток входа.
