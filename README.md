# Support Desk — backend (локальный запуск)

## Быстрый старт

1. Скопируйте `.env.example` в `.env` (для локальной разработки значения по умолчанию уже подходят).
2. Поднимите стек:

   docker-compose up --build

3. API поднимется на http://localhost:8000, документация (Swagger) — http://localhost:8000/docs
4. Засейте тестовыми данными (5 клиентов, тикеты за последние 90 дней):

   docker-compose exec backend python -m app.seed

## Структура

- `backend/app/models.py` — модели SQLAlchemy (схема из architecture.md, раздел 2)
- `backend/app/routers/` — эндпоинты по контракту из architecture.md, раздел 4
- `backend/app/seed.py` — генератор тестовых данных для локальной разработки

## Что уже готово

**Backend-ядро** — CRUD по клиентам, тикетам, настройкам, обещаниям.

**LLM-конвейер** (`app/llm.py`, `app/scheduler.py`):
- `POST /ingest/message` — при первом сообщении клиента создаёт тикет и сразу
  фоновой задачей запускает категоризацию через LLM (провайдер и модель
  берутся из `/settings`).
- Планировщик (APScheduler, работает внутри процесса backend) поднимает три джобы:
  - **categorize** — раз в минуту подстраховочно дозаполняет тикеты с
    категорией `"Не определено"` (на случай, если фоновая задача при ingest
    не успела/упала);
  - **autoclose** — раз в 10 минут ищет открытые тикеты без активности
    дольше `attention_after_min` и с уверенностью ИИ выше
    `auto_confidence_pct`, переводит их в `pending_confirm` (работает только
    если тумблер `auto_close` в настройках включён);
  - **daily_digest** — каждый день в 23:00 по Europe/Moscow генерирует
    дневную сводку и сохраняет в `daily_summaries`.
- `POST /digest/regenerate` — пересобрать сводку прямо сейчас, не дожидаясь 23:00.
- `POST /digest/send` — сохраняет sent_at у сводки (реальную отправку в
  Telegram добавит bot-digest в отдельном чате).

**Работа без ключа ИИ.** Если `ai_api_key` в `/settings` пустой (как из
коробки), категоризация и предложение автозакрытия используют простые
эвристики по ключевым словам, а сводка собирается по шаблону — приложение
не падает и не блокируется, просто без анализа от ИИ. Как только впишете
настоящий ключ через `PATCH /settings`, всё переключится на реальный LLM
без перезапуска.

**Промпты редактируются без изменения кода.** Три системных промпта
(категоризация, предложение автозакрытия, дневная сводка) хранятся в тех же
`/settings` под ключами `prompt_categorize`, `prompt_autoclose`,
`prompt_summary` — правите через `PATCH /settings`, `app/llm.py` их больше
не хардкодит. На фронте — карточка «Промпты ИИ» на странице «Настройки»
(сейчас ещё локальный mock-стейт, реальное сохранение подключится вместе с
интеграцией фронта в отдельном чате).

## Как проверить LLM-конвейер локально

1. Впишите ключ провайдера (например, Gemini — бесплатный тариф):
   ```
   curl -X PATCH http://localhost:8000/settings \
     -H "Content-Type: application/json" \
     -d '{"ai_provider": "gemini", "ai_model": "gemini-2.5-flash", "ai_api_key": "ВАШ_КЛЮЧ"}'
   ```
2. Создайте тестовое сообщение клиента — откроется тикет и запустится категоризация:
   ```
   curl -X POST http://localhost:8000/ingest/message \
     -H "Content-Type: application/json" \
     -d '{
       "tg_group_id": -100281773,
       "tg_message_id": 1,
       "sender_type": "client",
       "sender_name": "Тестовый клиент",
       "text": "Не приходят уведомления после обновления приложения",
       "sent_at": "2026-09-16T10:00:00Z"
     }'
   ```
3. Через несколько секунд проверьте тикет через `/docs` (`GET /tickets`) —
   категория и `ai_confidence` должны заполниться (без ключа — по эвристике,
   с ключом — от LLM).
4. Пересоберите сводку вручную, не дожидаясь 23:00:
   ```
   curl -X POST http://localhost:8000/digest/regenerate
   curl http://localhost:8000/digest/today
   ```

## Обновление существующей базы (без потери данных)

Если у вас уже есть работающая база с тестовыми данными (как сейчас) — новые
поля клиента (`vip`, `tariff_name`, `tariff_price`) в уже существующую
таблицу `clients` сами не добавятся (`create_all` создаёт только
отсутствующие таблицы, не меняет существующие). Выполните один раз после
обновления backend:

```
docker-compose exec db psql -U support -d support_desk -c \
  "ALTER TABLE clients ADD COLUMN IF NOT EXISTS vip BOOLEAN NOT NULL DEFAULT false;
   ALTER TABLE clients ADD COLUMN IF NOT EXISTS tariff_name VARCHAR;
   ALTER TABLE clients ADD COLUMN IF NOT EXISTS tariff_price VARCHAR;
   ALTER TABLE clients ADD COLUMN IF NOT EXISTS connected_at DATE;"
```

Данные (клиенты, тикеты, переписка) при этом не теряются — `down -v` в этот
раз делать не нужно.

  не появится этот модуль.
- **Название Telegram-чата** — по-настоящему через `GET
  /clients/{id}/telegram-info`, который дёргает Bot API `getChat` с тем же
  токеном, что у bot-collector. Если бот не подключён или нет доступа —
  корректно показывает «название чата недоступно», не падает.
- **Метрика «Активные уникальные чаты»** — новый эндпоинт `GET
  /metrics/active-chats`: считает уникальных клиентов с хотя бы одним
  сообщением от клиента за период. Кликабельная плашка на «Клиентах»,
  фильтрует таблицу.
- **Кликабельные метрики** — на «Клиентах» и в карточке клиента клик по
  плашке фильтрует/сортирует таблицу под ней (это и есть детализация — то,
  из чего посчитана цифра, видно в отфильтрованном списке). На «Сегодня» —
  частично: две метрики скроллят к соответствующему блоку, у «Обращений
  всего» и «Среднего времени ответа» пока нет отдельного места, куда
  вести — оставила некликабельными, а не подделывала переход в никуда.
- **Категория в панели тикета** — теперь select, с пунктом «+ Добавить
  категорию…»: вписанное значение сразу доступно для выбора (источник
  правды — уникальные категории, уже встречающиеся в тикетах, отдельной
  таблицы под это не заводили).
- **Статус — в хедере панели**, тоже select, с цветом под статус.
- **Обещания** — фильтры по клиенту, VIP и «срок ≤ 3 дней», работают
  вместе (AND), плюс существующий фильтр активные/закрытые.
- **Тумблеры** — увеличила (44×26, кружок 20px с тенью), не видя референс
  по ссылке (нет доступа к произвольным изображениям в вебе) — ориентир

- **Адаптив** — сайдбар на ширине <880px схлопывается в верхнюю панель с

  переносятся по строкам. Не видя скриншот-референс проблемы, не могу
  гарантировать, что это именно тот случай наложения — тестируйте и
  присылайте конкретные места, если что-то всё ещё ломается.

### Несколько тем в одном чате — маршрутизация по категориям

Раньше действовало правило «один открытый тикет на клиента» — если клиент,
не дожидаясь закрытия текущего тикета, писал о чём-то совсем другом, это
приклеивалось к старому тикету и путало категорию. Теперь (`routers/ingest.py`):

1. **Явный Telegram-реплай** — если клиент или агент отвечают на конкретное
   сообщение (в Telegram — «ответить»), backend точно знает, к какому
   тикету это относится, без ИИ. Реплай на уже закрытый тикет открывает
   его заново.
2. **Сообщение клиента без реплая** — категоризируется сразу же (синхронно,
   не фоновой задачей, как раньше), и ищется открытый тикет **этого же
   клиента с такой же категорией**. Если такого нет — заводится новый.
   Так «Баг» и «Вопрос по тарифу» в одном чате живут в разных тикетах, даже
   если клиент пишет о них вперемешку.
3. **Сообщение агента без реплая** — фолбэк на последний активный открытый
   тикет клиента (старое поведение): если тем несколько параллельно и
   агент не указал реплаем, на какую отвечает, точнее не определить.

Компромисс: если клиент пишет два сообщения на одну тему, но ИИ ставит им
чуть разные категории (например, «Баг» и «Вопрос по функционалу» для
пограничного случая) — они разъедутся по разным тикетам, хотя это
одна тема. Реплай — самый надёжный способ избежать этого, но полагается на
то, что люди реально им пользуются. Точнее, но дороже (лишний вызов ИИ на
сообщение) — задавать модели отдельный вопрос «это продолжение той же
темы или новая» вместо матчинга по категории; можно добавить, если
матчинг по категории на практике окажется недостаточно точным.

bot-collector теперь передаёт `reply_to_tg_message_id`, если сообщение —
ответ на другое; в остальном логика бота не поменялась.

### Оркестрация нескольких провайдеров ИИ

Вместо одного активного провайдера — список в `/settings` под ключом
`ai_providers`, с приоритетом сверху вниз:
```json
[
  {"provider": "gemini", "model": "gemini-2.5-flash-lite", "api_key": "...", "enabled": true},
  {"provider": "groq", "model": "llama-3.3-70b-versatile", "api_key": "...", "enabled": true},
  {"provider": "openrouter", "model": "deepseek-v4", "api_key": "", "enabled": false}
]
```
`app/llm.py` пробует включённых провайдеров по очереди: пустой ключ,
выключен или запрос упал (сеть, невалидный ключ, `429` — превышен лимит) —
переход к следующему. Если ни один не ответил — как и раньше, включается
эвристика по ключевым словам. Настраивается в «Настройки» → «Провайдеры
ИИ», порядок фиксированный (Gemini → Groq → OpenRouter), но каждого можно
включить/выключить и задать свою модель и ключ независимо.

По умолчанию модель Gemini сменили на `gemini-2.5-flash-lite` — у нашей
задачи (короткая классификация/сводка) разница в качестве с обычным Flash
несущественна, а бесплатный лимит заметно выше.

### Аналитика — сравнение периодов

Новая вкладка «Аналитика» в сайдбаре. Сравнивает выбранный период с
предыдущим периодом такой же длины (`GET /metrics/period-comparison`):

- Общее число обращений и дельта (кирпичный — рост числа обращений, зелёный
  — снижение; рост числа обращений считается сигналом, требующим внимания,
  а не «хорошей новостью» — это про нагрузку на поддержку, а не про
  бизнес-метрику вроде выручки).
- Разбивка «за счёт чего» на три группы, кликабельные — под каждой
  раскрывается список конкретных клиентов с их вкладом в изменение:
  - **Новые клиенты** — `connected_at` (дата подключения, приходит с
    Oracle-синка) младше 60 дней. Порог зашит в
    `NEW_CLIENT_THRESHOLD_DAYS` в `app/routers/clients.py` и
    `app/routers/metrics.py` (специально не вынесли в общий модуль ради
    одной константы — если появится третье место использования, стоит
    вынести).
  - **Действующие клиенты** — все остальные, дельта по ним между периодами.
  - **Замолчавшие** — писали в прошлом периоде, в этом — ни одного
    обращения (сигнал оттока).
- Разбивка по категориям — было/стало/дельта с мини-полосой.

Поле `connected_at` у клиента, как и тариф, пока не заполняется реальными
данными (Oracle-синк не собран) — в сидинге проставлено вручную для теста
(один клиент «новый» — 25 дней назад, остальные — давние).

### Категории, платная доработка, название чата, гибкая сводка, SLA по рабочим часам

- **Фильтр по категориям** в «Обращениях» — множественный выбор (переиспользуемый `MultiSelect`), варианты подтягиваются из `GET /categories`.
- **Платная доработка** — новые поля тикета: `is_paid_work`, `planned_cost` (плановая стоимость), `actual_hours` (факт. часы), `actual_cost` (факт. стоимость). Бейдж и фильтр — в «Обращениях», «Сегодня», «Обещания»; сами поля редактируются в панели тикета (появляются при включении тумблера «Платная доработка»).
- **Обещания** — фильтр по клиенту и по названию чата в Telegram теперь множественный выбор (`MultiSelect`), комбинируется с остальными фильтрами по И.
- **Название чата в TG** — везде, где показывается клиент, рядом выводится `client.chat_label` (короткое имя чата, приходит с Oracle-синка вместе с тарифом — это НЕ то же самое, что название чата, полученное через Telegram Bot API `getChat` в карточке клиента, это разные источники данных, оба по-своему «имя чата в TG»).
- **Время дневной сводки** — настраивается в «Настройки» → «Автоматика» (поле времени рядом с тумблером). Планировщик проверяет каждые 5 минут вместо фиксированного cron на 23:00 — смена времени в `/settings` подхватывается сама, без перезапуска backend.
- **Рабочие часы и SLA** — новая карточка в «Настройки»: начало/конец рабочего дня, рабочие дни недели (чипы Пн-Вс), список праздничных дат. Время ожидания ответа (`wait_business_min`, считается в `app/business_hours.py`) теперь исключает выходные, праздники и нерабочие часы — это же значение используется и для «Нарушен SLA» в «Обращениях», и для среднего времени ответа клиента, и для порога автозакрытия. Часовой пояс расчёта — всегда Europe/Moscow, независимо от таймзоны сервера (актуально теперь, когда стек крутится на сервере с UTC, а не на вашем Маке).

Миграция для существующей БД — три новых столбца у тикетов:
```
docker compose exec db psql -U support -d support_desk -c \
  "ALTER TABLE tickets ADD COLUMN IF NOT EXISTS is_paid_work BOOLEAN NOT NULL DEFAULT false;
   ALTER TABLE tickets ADD COLUMN IF NOT EXISTS planned_cost VARCHAR;
   ALTER TABLE tickets ADD COLUMN IF NOT EXISTS actual_hours DOUBLE PRECISION;
   ALTER TABLE tickets ADD COLUMN IF NOT EXISTS actual_cost VARCHAR;"
```
(на сервере команда `docker compose`, локально — `docker-compose`, через дефис)

### Клиенты, Обращения, «Пульс поддержки» — большой раунд доработок

**URL-роутинг** — приложение больше не однa «страница», адрес в браузере
теперь отражает, где вы находитесь: `/clients`, `/clients/{id}`, `/feed`,
`/pulse` («Сегодня» переименован в «Пульс поддержки»), `/promises`,
`/analytics`, `/settings`. Открытая панель тикета добавляет `?ticket={id}`
к текущему адресу — ссылку можно скопировать и переслать, откроется
именно в этом месте. Кнопки «Назад»/«Вперёд» браузера работают. Роутинг
самописный (`history.pushState`/`popstate`), без сторонних библиотек.

**Клиенты:**
- фильтр периода убран из таблицы (обычная статистика за 30 дней), период
  остался только в карточке конкретного клиента;
- починен баг с полной перезагрузкой страницы при переключении VIP —
  причина была в том, что общий счётчик обновлений (`refreshTick`) сбрасывал
  всё состояние карточки клиента в `null` при любом изменении где угодно в
  приложении; теперь VIP и название чата обновляются локально из ответа API,
  без лишнего мигания;
- `POST /clients` — создание клиента вручную (кнопка «Добавить клиента»),
  `DELETE /clients/{id}` — удаление вместе со всей историей (сообщения,
  тикеты), с подтверждением на фронте;
- фильтр по тарифам (множественный выбор) + колонка «Тариф» в таблице;
- фильтр по статусу подписки (множественный выбор), по умолчанию — только
  статусы, которые выглядят «активными» (та же логика, что красит бейдж
  статуса зелёным/красным в карточке).

**Обращения:** кнопка «Создать обращение» (`POST /tickets`, привязка к
клиенту вручную), клик по имени клиента в панели тикета ведёт на карточку
клиента, фильтр «Закрытые», поле «Обещание клиенту» — textarea.

**Пульс поддержки** (бывший «Сегодня»):
- новый блок «Задачи со сроком и Jira» — обращения с одновременно заданными
  сроком и ссылкой на задачу, показаны отдельно и исключены из остальных
  блоков ниже, чтобы не дублировались;
- убран фильтр «Только платные доработки» — признак доработки остаётся
  видным прямо на карточке тикета (зелёный блок с переключателем);
- сводка от ИИ теперь в самом верху страницы, над плашками метрик;
- добавлены фильтры VIP / тариф / статус подписки / конкретный клиент —
  действуют на все блоки странице разом.

### Индексы БД

Их не было вообще — `create_all()` создавал таблицы без индексов, план из
исходного архитектурного документа (`CREATE INDEX ...`) так и не
переехал в реальные модели SQLAlchemy. Добавлены на `tickets.client_id`,
`tickets.status`, `tickets.first_message_at`, `messages.client_id`,
`messages.sent_at`, `messages.ticket_id` — на новых установках создадутся
сами через `create_all()`, для существующей БД нужна миграция (см. раздел
про обновление базы, там же и остальные `ALTER TABLE`/`CREATE INDEX`
команды по всем прошлым раундам).

Отдельно: `GET /clients` раньше был N+1 (2 запроса на каждого клиента —
итого 2×N на список) — переписан на 3 запроса суммарно независимо от
числа клиентов (сами клиенты, все тикеты периода одним `IN`, открытые
счётом одним `GROUP BY`), дальше агрегация в Python без обращений к БД.

### Маршрутизация при недоступном ИИ + объединение/разделение/удаление тикетов

**Раньше** сообщение клиента без реплая всегда матчилось по категории —
и при работающем ИИ, и при эвристике-заглушке. Проблема: эвристика по
ключевым словам куда менее стабильна в определении темы, чем реальный
ИИ — соседние сообщения одного разговора могли получить разные категории
и разъехаться по разным тикетам.

**Теперь** (`llm.categorize_ticket` возвращает четвёртым значением
`used_ai: bool`, `routers/ingest.py`):
- ИИ ответил → матчинг по категории, как раньше;
- ИИ недоступен (нет ключа/лимит/сеть — сработала эвристика) → категория
  игнорируется, сообщение уходит в **последний открытый тикет клиента**,
  чтобы разговор оставался цельным. Нет открытого — заводится новый, как
  обычно.

**Новые ручные операции над тикетами** — на случай, когда всё же
разъехалось (или наоборот, нужно разделить один раздутый тикет):
- `POST /tickets/merge` — объединяет два тикета одного клиента:
  переписка `merge_ticket_id` переезжает в `keep_ticket_id`, первый
  удаляется. `first_message_at`/`first_response_at` результата — самые
  ранние из двух.
- `POST /tickets/{id}/split` — выносит выбранные `message_ids` в новый
  тикет того же клиента, с указанной (или унаследованной) категорией.
- `DELETE /tickets/{id}` — удаляет тикет; сообщения не удаляются, просто
  отвязываются (`ticket_id → NULL`), история переписки в БД остаётся.

На фронте — в панели тикета, в самой «Переписке»: кнопка «Разделить
обращение» включает чекбоксы у сообщений, выбрали нужные → форма темы и
категории → новый тикет. Ниже, в «Действия с обращением» — объединение
(выбор из других открытых тикетов этого же клиента) и удаление.

### Поиск Telegram id участников переписки

Раньше бот сохранял только имя отправителя (`sender_name`) — ненадёжный
идентификатор, по имени нельзя точно добавить человека в агенты. Теперь

### Белые области при скролле + несинхронное обновление данных

**Белые области при скролле (пружинный эффект на Mac):** `html`/`body`
не имели заданного фона — при overscroll-эффекте трекпада браузер на
мгновение показывает то, что физически «за краями» страницы, а это
белый цвет по умолчанию вместо тёплого фона приложения. Задан фон в
`index.html` + `overscroll-behavior: none`.

**Данные не обновлялись без перехода в другой раздел и обратно:**
у `ClientDetailPage` был намеренный компромисс из более раннего фикса —
чтобы починить баг с полной перезагрузкой карточки при переключении VIP,
`refreshTick` убрали из зависимостей эффекта загрузки данных целиком. Это
остановило мигание, но заодно отключило реакцию на изменения **из других
мест** (например, правите тикет в панели — история обращений в открытой
карточке клиента не подтягивала это без повторного захода).

Исправлено правильно, а не тем же топорным способом: у эффекта загрузки
теперь есть «ключ текущего контекста» (клиент+период). Если ключ
изменился — это настоящая навигация, показываем экран загрузки как
обычно. Если ключ тот же, а сработал только `refreshTick` — тихо
подгружаем новые данные в фоне и подменяем на экране без сброса в `null`,
без мигания. Тот же паттерн применён и к `AnalyticsPage`, которая раньше
вообще не была подписана на общие обновления.

Остальные разделы (Клиенты, Обращения, Пульс поддержки, Обещания,
Настройки) уже были устроены правильно — специально проверила каждый.

### Панель тикета — режим разделения и меню «⋯» по новому прототипу

Прототип: `https://claude.ai/artifact/WNKTtKLQ2E6qN2dcD2qwWG` (обновлённая

- **После создания** — панель возвращается в обычный режим, показывается

  тикета).
- **Меню «⋯» в шапке** заменило блок «Действия с обращением»: «Разделить

### Статус «Ожидание ответа клиента» + переверстка «Очереди» по прототипу

Прототип: `https://claude.ai/artifact/FCCPnVMzyixCT6ykL4pTqB` (обновлённая версия).

**Новый статус `waiting_client`** — переходы полностью автоматические, в
`routers/ingest.py`:
- агент ответил → тикет переходит в `waiting_client` (ход у клиента);
- клиент написал снова (тикет был в `waiting_client`) → автоматически
  переоткрывается в `open`.

**SLA не растёт, пока ход за клиентом** — `business_hours.py` переписан
на единую функцию `ticket_response_status`, три состояния:
- `no_response` — ответа не было, минуты растут от первого сообщения;
- `waiting_us` — уже отвечали, но пришли новые сообщения от клиента без
  ответа — минуты растут от последнего такого сообщения;
- `waiting_client` — ответили, новых сообщений нет — минуты **зафиксированы**
  на времени до первого ответа, не растут, пока не ответит клиент.

Отдельная функция `first_response_business_minutes` — для метрики
«среднее время ответа» у клиента, которая должна оставаться историческим
фактом, а не текущим состоянием (иначе новая логика её бы испортила).

Агрегаты по сообщениям (кто ответил последним, сколько новых сообщений от
клиента) считаются одним запросом на весь список тикетов —
`bulk_message_aggregates`, не N+1.

**Старая AI-подсказка «Ждём подтверждения»/`pending_confirm`** —
задача автозакрытия в планировщике отключена (её условие — открытый
тикет с уже проставленным первым ответом — больше физически не
встречается, раз ответившие тикеты сразу уходят в `waiting_client`).
Статус и его отображение оставлены в коде для обратной совместимости со
старыми тикетами, но новых больше не появится.

**Переименовано** «Агент»/«агент» → «Команда PRM»/«команда PRM» везде,
где это метка роли в переписке.

**Карточка обращения в очереди:**
- зелёная метка «● N новых» у заголовка, если есть непроверенные
  сообщения от клиента без ответа с нашей стороны;
- статус ответа тремя видами текста (без фона/рамки, только цвет + точка):
  «без ответа · X» (янтарный до часа, красный дольше), «ждёт X» (обычный
  текст), «1-й ответ за X» (янтарный, если первый ответ занял больше часа);
- сортировка внутри группы — сначала без единого ответа, дальше по
  времени ожидания.

**Группа «Ждут ответа клиента»** — не привязана к дню (в отличие от
«Открыто сегодня»/«С прошлых дней»), не входит в счётчик «Открыто
сейчас». На вкладке «Все» свёрнута до одной строки со счётчиком (клик
разворачивает), есть отдельная вкладка «Ждут клиента» с полным списком.

**Фильтр «Есть новые сообщения»** — новый чип в «Очереди».

**Блок «Просроченные обязательства»** — новый, в красной рамке, наверху
правого сайдбара (выше «Ближайших обязательств» и «Обязательств»),
показывает на сколько дней просрочено, срок и ссылку на Jira, если есть.
Метрика «Просрочено обещаний» переименована в «Просрочено обязательств»,
подсвечена красным.

Миграций нет — новый статус живёт как обычная строка, без изменений схемы.

### Пять доработок «Очереди»

1. **Цвет чипа роли в переписке** — «команда PRM» и «клиент» раньше были
   визуально идентичны (оба зелёные). Теперь «команда PRM» — зелёный
   (выделяется, это ответ), «клиент» — нейтральный серый.
2. **Дедупликация с блоками обязательств** — обращение со сроком
   исполнения (`due_date` заполнен) больше не показывается одновременно
   и в обычных группах очереди («С прошлых дней»/«Открыто
   сегодня»/«Ждут ответа клиента»), и в блоках обязательств справа —
   только в блоках обязательств.
3. **Сворачиваемые группы** — «С прошлых дней», «Открыто сегодня»,
   «Закрытые» сворачиваются кликом по заголовку (состояние держится
   в React, не сохраняется между перезагрузками страницы).
4. **Порядок групп** — «Закрытые» теперь идут последними, после «Ждут
   ответа клиента» (было наоборот).
5. **Отметка «прочитано»** — новая колонка `tickets.agent_seen_at` и
   эндпоинт `POST /tickets/{id}/mark-seen`. Гасит только чип «N новых» —
   не влияет на статус/SLA, это осознанно разные вещи (прочитать ≠
   ответить). Сам чип теперь кликабельная кнопка — клик по нему сразу
   гасит бейдж, не открывая панель тикета. Плюс тикет автоматически
   отмечается прочитанным при открытии его панели.

Миграция для существующей БД:
```
docker compose exec db psql -U support -d support_desk -c "ALTER TABLE tickets ADD COLUMN IF NOT EXISTS agent_seen_at TIMESTAMPTZ;"
```

### Авторизация — первый этап

Логин/пароль + вход через Google, JWT в localStorage, журнал действий.
Ролевой модели пока нет (осознанно — второй этап, как договаривались).

**Новые таблицы** — `users`, `audit_log`. Создаются сами при перезапуске
backend (`create_all()` создаёт только отсутствующие таблицы, ничего не
трогает в существующих) — отдельной миграции не нужно.

**Все API-эндпоинты теперь требуют вход**, кроме:
- `POST /ingest/message` — сюда стучится bot-collector, ему неоткуда
  взять токен браузерного пользователя;
- `POST /auth/login`, `POST /auth/google`, `GET /auth/config` — иначе
  входить было бы нечем.

**Первого пользователя создаёт CLI-скрипт**, не сам себя — все ручки
API защищены, регистрироваться через них некому:
```
docker compose exec backend python -m app.create_admin you@example.com "Ваше Имя"
```
Спросит пароль интерактивно (не через аргумент — не остаётся в истории
шелла). Дальше новых пользователей можно заводить уже из интерфейса —
«Настройки» → «Пользователи».

**Смена пароля** — «Настройки» → «Мой аккаунт», доступно каждому вошедшему
для своего же пароля. Администратор может сбросить пароль другому
пользователю через «Сбросить пароль» в списке пользователей — без ввода
старого пароля пользователя (это же логично, он его не знает).

**Вход через Google** — требует `google_client_id` из Google Cloud
Console (Настройки → «Вход через Google»). Client ID не секрет, secret не
нужен вообще — используется id_token-флоу целиком на стороне браузера.
**Жёстко требует HTTPS** — Google не разрешает redirect на `http://` в
продакшене. Пока сайт на обычном HTTP, кнопка Google просто не появится
на экране входа (проверяется через `/auth/config`), а логин/паролем
работает уже сейчас, без всяких условий.

**Журнал действий** — новый раздел в сайдбаре. Логируются: создание/
изменение/удаление/объединение/разделение тикетов, создание/изменение/
удаление клиентов, сохранение настроек (только НАЗВАНИЯ изменённых
ключей — сами значения, включая API-ключи ИИ и пароль Oracle, туда
сознательно не попадают), переименование категорий, починка ролей
отправителей. Не заведено ещё логирование для промисов и части более
редких операций — можно добавить по необходимости, сам механизм
(`auth.log_action`) уже готов и используется в остальных местах.

  восстилизованы под новый визуал; сама логика фильтрации не менялась.

Backend не менялся, миграций нет.

### «Обращения» — доработки после первой версии таблицы

- **Период** — теперь кнопка «Период: 30 дней ▾» в строке фильтров (а не
  отдельная полоса над таблицей): Сегодня / Вчера / 7 / 30 / 90 дней / Всё
  время / Произвольный (две даты). Панель рисуется через портал в `<body>`.
- **Колонка «Срок»** в таблице + сортировка по ней (обращения без срока
  всегда внизу, в любом направлении). Просроченный срок — красным, ближайшие
  3 дня — янтарным.
- **SLA не считается, если задан срок исполнения** (пока обращение не
  закрыто): такие обращения не попадают в «Нарушен SLA», в красную плашку
  над таблицей, не подсвечиваются как нарушение, в колонке «Ожидание»
  пишется «SLA не считается», в панели тикета вместо шкалы — пометка.
  На backend то же условие в `GET /tickets?view=sla_breach`.
- Вкладка «Без задачи в Jira» → **«Задачи со сроком»** (незакрытые с
  заданным сроком).
- **Новое поле «Комментарий»** у тикета (`tickets.comment`, TEXT) —
  расширенное поле под «Обещанием клиенту» в панели тикета и отдельное поле
  в форме создания.
- «Тема обращения» → **«Наименование обращения»** в панели тикета и в форме
  создания (там теперь однострочное поле, как в панели редактирования).
- В форме создания поле Jira принимает и просто ключ (`CLOUDDEV-1768`), и
  полный URL — как в панели редактирования.
- **Экспорт (CSV)** теперь содержит: тему, комментарий, обещание клиенту,
  срок исполнения и **полную** ссылку на задачу Jira (ключ разворачивается
  через базовый URL из настроек).

Миграция (обязательна, выполнить ДО обновления кода):
```
docker compose exec db psql -U support -d support_desk -c "ALTER TABLE tickets ADD COLUMN IF NOT EXISTS comment TEXT;"
```

### Бот после появления авторизации

Все эндпоинты требуют вход, включая `/settings`, откуда бот брал токен и
список агентов, — бот стал получать 401 и падал (сообщения перестали
приходить). Теперь бот берёт настройки из `GET /ingest/bot-config`, закрытого
общим ключом `BOT_SERVICE_KEY` (одно и то же значение у backend и
bot-collector, задаётся в `.env` рядом с `docker-compose.yml`):
```
echo "BOT_SERVICE_KEY=$(openssl rand -hex 24)" >> .env
docker compose up -d --build
```
Если настройки получить не удалось (backend перезапускается, неверный ключ),
бот больше не отключается от Telegram — остаётся на текущем соединении и
повторяет попытку.

Известный пробел: `POST /ingest/message` по-прежнему открыт без ключа — при
желании его можно закрыть тем же `BOT_SERVICE_KEY`.

### Длинные тексты в панели тикета

- Текст сообщений переносится по любым символам (`overflow-wrap: anywhere`) —
  длинные токены и ссылки без пробелов больше не вылезают за пузырь и панель;
  переводы строк в сообщениях теперь сохраняются (`white-space: pre-wrap`).
- Область прокрутки панели не сдвигается по горизонтали.
- Название обращения — поле, растущее по высоте (`TitleInput`), а не
  однострочный input: длинное название читается целиком. Enter в нём
  игнорируется, вставленные переносы строк заменяются пробелом.

### Порядок сообщений и название при разделении

- Telegram отдаёт время сообщения с точностью до секунды, а очень длинное
  сообщение режет на части с одинаковым временем. Сортировка только по
  времени давала случайный порядок таких частей, после переноса в другой
  тикет он мог меняться. Теперь порядок: время → `tg_message_id` (растёт
  строго по порядку отправки в чате) → `id`.
- Название нового тикета при разделении: переносы строк схлопываются, длина
  до 120 символов (раньше — до 200 вместе с переносами).

### Сайдбары закрываются только осознанно

Панель обращения и панель создания обращения больше не закрываются кликом по
затемнённой области и по `Esc` — только крестиком или кнопкой «Отмена».
Меню «⋯» в панели обращения по-прежнему закрывается кликом вне меню (это
всплывающее меню, а не сайдбар). Модалка «Добавить клиента» не менялась.

### Журнал действий не должен ломать действие

`auth.log_action` писал в JSONB словарь изменённых полей как есть; если там
был срок исполнения (объект `date`), запись падала, и уже после сохранения
тикета пользователь получал 500 (в браузере — «Нет связи с backend / Failed
to fetch», т.к. ответ 500 идёт без CORS-заголовков). Теперь `details`
приводятся к JSON-виду (`date`/`UUID` → строки), а любой сбой записи в журнал
откатывается и пишется в лог `[audit] ...`, не влияя на ответ.

- Amber (жёлтый) как «средний» уровень тревоги — оставила, хотя в
  ТЗ названы только зелёный и кирпичный; без жёлтого пропадает
  промежуточная ступень между «норма» и «критично», решила не убирать.
- Радиус 8px применён к карточкам (`Card`, `KpiCard`); у мелких элементов

  специально под 8, в ТЗ радиус был только про карточки.
- Клик по метрикам «Обращений всего» и «Среднее время ответа» на
  «Сегодня» — без действия (см. выше).

## oracle-sync — синхронизация клиентов

Локальный агент (папка `oracle-sync/`, **не** в docker-compose — живёт на
машине с доступом к Oracle, не на сервере). Полная инструкция —
`oracle-sync/README.md`, коротко:

- Забирает SQL-запрос из `/settings` (тот же, что в UI «Настройки» →
  «Синхронизация из Oracle») — один источник правды, не хардкодит запрос у
  себя.
- Отправляет результат в `POST /clients/sync`.
- Два режима: `--once` (для cron) и `--loop` (сам проверяет раз в минуту,
  не нажали ли «Запустить синхронизацию» в дашборде — флаг
  `oracle_sync_requested`, backend сам сбрасывает его и проставляет
  `oracle_last_sync` после успешного синка).
- Время последнего синка видно в сайдбаре и в карточке настроек — теперь
  это реальные данные, не заглушка.
- Ожидает конкретные алиасы колонок в SQL: `name, tg_group_id, chat_label,
  tariff_name, tariff_price, connected_at` (обязательны только первые два).

## frontend — веб-интерфейс

Реальный React-проект (Vite), подключён к backend через `VITE_API_URL`.
Мокового режима больше нет — все страницы читают и пишут через API.

### Запуск

Фронтенд не в docker-compose — для локальной разработки проще и быстрее
через обычный dev-сервер с горячей перезагрузкой:

```
cd frontend
npm install
npm run dev
```

Откройте **http://localhost:5173** — backend должен быть уже поднят
(`docker-compose up` в корне проекта) и доступен на `http://localhost:8000`,
это адрес по умолчанию (можно переопределить через `.env`, см.
`.env.example` в папке `frontend`).

### Что уже подключено к реальным данным

- Клиенты, тикеты, категории по темам, обещания, сегодняшняя сводка,
  настройки (модель ИИ, токены ботов, список агентов, промпты, пороги SLA,
  SQL-запрос Oracle-синка) — всё читается и сохраняется через API.
- Боковая панель тикета сохраняет статус, обещание, ссылку на Jira и срок
  через `PATCH /tickets/{id}`.
- Кнопки «Перегенерировать»/«Отправить в чат» на странице «Сегодня» дёргают
  `/digest/regenerate` и `/digest/send`.

### Последние доработки

- Панель тикета — шире (460px), категория и тема теперь редактируются
  вручную (с быстрыми чипами частых категорий), плюс кликабельная ссылка
  «Открыть в Jira».
- Ссылка на Jira теперь кликабельна везде, где показывается (лента
  обращений, обещания, панель тикета) — короткие коды вида `SUP-1039`
  превращаются в ссылку через `jira_base_url` из настроек (новое поле в
  разделе «Настройки» → «Jira»); полные URL работают и без base_url.
- Раздел «Обращения» — фильтр по периоду (Сегодня / Вчера / 7 / 30 / 90 дней).
- Раздел «Сегодня» — убрана демо-нагрузка на агентов; добавлены блоки
  «Незакрытые с предыдущих дней» (с кнопкой быстрого закрытия) и
  «Обещания — срок в ближайшие 3 дня».
- Раздел «Обещания» — теперь показывает и закрытые тикеты (бакет
  «Выполнены»), фильтр Открытые/Закрытые/Все, колонка категории, клик по
  строке открывает полную карточку тикета (подгружается на лету через
  `GET /tickets/{id}`).
- Backend: `PromiseOut` расширен полями `category` и `status`;
  `TicketUpdate` — полем `subject`; `/promises` больше не скрывает закрытые
  тикеты молча.

### Известные упрощения этой версии

- **Нагрузка на агентов** на странице «Сегодня» — демо-данные, backend пока
  не ведёт учёт агентов и их загрузки (нет такой модели данных).
- **Вкладка «Повторные»** на странице «Обращения» убрана — в мок-версии
  она определялась искусственно, в backend такого признака нет.
- **Тренд за 6 недель** в таблице клиентов (был в мок-версии как мини-график
  в каждой строке) убран с общего списка — потребовал бы N+1 запросов на
  каждую строку таблицы; на карточке отдельного клиента график динамики
  остался, там это один дополнительный запрос, а не N.
- **Цитата сообщения с автором** в боковой панели тикета убрана — backend
  отдаёт только `subject` (сформулированную тему), не сырой текст с именем
  автора; чтобы вернуть — понадобится отдельный эндпоинт вида
  `GET /tickets/{id}/messages`.
- Кнопка «Запустить синхронизацию» с Oracle пока не показывается — сам
  локальный агент синка ещё не собран (следующий пункт плана), SQL-запрос
  только сохраняется в настройках.

## bot-collector — приём сообщений из Telegram

### Шаг 1. Создать бота

1. Откройте в Telegram **@BotFather** → `/newbot` → следуйте инструкциям.
2. Сохраните токен, который он выдаст (выглядит как `123456:ABC-DEF...`).

### Шаг 2. Отключить Privacy Mode — САМЫЙ ЧАСТЫЙ ПРОКОЛ

По умолчанию у ботов включён Privacy Mode: они видят в группах **только**
сообщения, адресованные лично им (команды `/...`, реплаи на их сообщения).
Обычные реплики клиентов бот просто не получит, пока это не отключить.

У **@BotFather**: `/mybots` → выбрать бота → `Bot Settings` → `Group Privacy`
→ `Turn off`.

Если бот уже был добавлен в группу до отключения — удалите его из группы и
добавьте заново (либо сделайте администратором группы, это тоже обходит
Privacy Mode, независимо от настройки).

### Шаг 3. Запустить стек

```
docker-compose up --build
```
В логах `bot-collector` появится: `bot_collector_token пуст в /settings —
бот не подключён к Telegram` — это ожидаемо, токен ещё не задан.

### Шаг 4. Задать токен и список агентов через /settings (не через .env!)

```
curl -X PATCH http://localhost:8000/settings \
  -H "Content-Type: application/json" \
  -d '{
    "bot_collector_token": "<токен от BotFather>",
    "agent_tg_ids": [123456789]
  }'
```
Свой Telegram id — у **@userinfobot**. Список агентов можно оставить пустым
`[]`, если пока некому отвечать в тестовой группе — тогда все сообщения
будут считаться сообщениями клиента, это нормально для первого теста.

В течение `TOKEN_POLL_INTERVAL_SEC` (по умолчанию 20 секунд) бот сам
подключится и подхватит список агентов — без перезапуска контейнера. Обе
настройки можно менять этой же командой в любой момент, бот сам
переподключится/обновит список.

### Шаг 5. Подключить тестовую группу

Клиент должен быть известен backend'у заранее (обычно это делает Oracle-синк,
но его ещё нет — регистрируем вручную для теста):

1. Создайте тестовую группу в Telegram, добавьте туда бота.
2. Напишите в группе любое сообщение.
3. В логах `bot-collector` увидите предупреждение вида
   `Группа -1001234567890 ещё не синхронизирована` — скопируйте это число.
4. Зарегистрируйте клиента с этим id:
   ```
   curl -X POST http://localhost:8000/clients/sync \
     -H "Content-Type: application/json" \
     -d '{"clients": [{"name": "Тестовый клиент", "tg_group_id": -1001234567890}]}'
   ```
5. Напишите в группе ещё раз — теперь должен создаться тикет. Проверьте:
   ```
   curl http://localhost:8000/tickets
   ```

### Ограничения текущей версии

- Обрабатываются только текстовые сообщения (фото/файлы/голосовые — позже).
- Бот работает через long polling — не нужен публичный адрес, подходит и
  для локальной разработки, и для сервера без домена.
- Токен хранится в БД в открытом виде (как и `ai_api_key`) — шифрование
  чувствительных настроек стоит добавить перед деплоем в открытый доступ.

## О миграциях

Для скорости локальной разработки таблицы создаются автоматически при
старте приложения (`Base.metadata.create_all`), без отдельного шага
миграции. Когда схема стабилизируется и появится необходимость в
продакшен-деплое с контролируемыми изменениями — добавим Alembic поверх
уже готовых моделей (это не потребует переписывания моделей, просто
`alembic revision --autogenerate` на текущей схеме).
